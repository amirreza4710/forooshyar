# ADR-010 — Forooshyar Plus Capability Integration

**Status:** Accepted
**Date:** 2026-09-29
**Component:** Product / Architecture / Governance
**Naming:** superseded by ADR-011

## Context

The user-approved `BAZARAK_FOROOSHYAR_MERGED_SPEC.md` defines additional field-operations and automation capabilities. Forooshyar already supplies the sales and operational-data core; the Bazarak capability baseline supplies the field-operations and automation layer. Running them as separate products would duplicate customer, order, and operational data.

## Decision

```text
Forooshyar Plus
├── Sales Core
├── Field Operations
├── Cash Operations
└── Automation (after the core data flow is reliable)
```

- **Forooshyar Plus** is the product name under ADR-011.
- **Bazarak** is the source label for the integrated Field Operations and Automation capabilities.
- PostgreSQL remains the system of record; React, Vite, Express, Drizzle, OpenAPI, and the modular monolith remain unchanged.
- The MVP now admits three narrowly-scoped capabilities: visits, operational alerts, and logged automation workflows. Route optimisation, AI, bots, offline synchronisation, a marketplace, and a platform shell remain outside the MVP.
- A Visit → Order association is required, but the existing order representation must not be refactored merely for this integration.
- n8n is an automation integration target, not permission to add a dependency or deployment service before its automation slice is admitted and designed.

## Consequences

- The frozen v2.4 backlog is retained as history; the active delivery plan is rebased to 41 committed features.
- New work remains gated by the active phase and feature acceptance criteria.
- This ADR does not authorize schema, API, UI, dependency, deployment, multi-tenancy, or platform-shell changes by itself.

## Acceptance for follow-up implementation

1. Visit data is organization-scoped, auditable, and connected to a customer and optionally an order.
2. Alerts and workflow executions are traceable and must not directly mutate inventory, orders, commissions, or payments.
3. Each implementation slice updates its OpenAPI contract, tests, and relevant operational evidence.
