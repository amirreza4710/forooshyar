# ADR-009 — Farakhorasan Platform / Forooshyar Sales Boundary & Product Naming

**Status:** Proposed — Review Required Before Implementation  
**Date:** 2026-08-20  
**Author:** Project Governance  
**Component:** Product / Architecture / Governance  
**Related:** ADR-0001, Checkpoint 1.6, Roadmap v2.4, Repository-Audit, CONFLICT-MATRIX

---

## 1. Context

Repository documentation currently uses several related names and scopes: Farakhorasan, Farakhorasan Sales OS, Forooshyar, and legacy branding references. At the same time, the repository is intended to support a multi-organization platform while the first MVP deployment starts with one organization.

Without an explicit boundary, future agents may incorrectly treat the sales product as the entire platform, introduce organization-level shell concerns into the sales module, or start implementation before the domain and scope decisions are reviewed.

A second risk is premature implementation of a future multi-organization/بازاردان shell before the platform/module relationship and scope have been approved.

---

## 2. Decision

### 2.1 Platform / Module Relationship

The temporary canonical relationship is:

```text
Farakhorasan Platform
└── Forooshyar Sales module
```

- **Farakhorasan Platform** is the platform-level boundary and future host for shared organization/tenant capabilities.
- **Forooshyar Sales** is the sales-domain module/product surface operating within that platform boundary.
- The current MVP is the Forooshyar Sales scope, not a complete implementation of the whole Farakhorasan platform.

This is a domain/product boundary decision. It does **not** authorize code restructuring in this PR.

### 2.2 Multi-tenancy Is Mandatory Infrastructure

Multi-tenancy is an architectural requirement, not an optional post-MVP feature.

The platform must preserve an organization/tenant boundary from the beginning, including the conceptual requirement for organization scoping of sensitive data.

However, this ADR does not authorize a schema migration. The concrete schema, API, access-control and rollout design must be specified and scope-reviewed before implementation.

### 2.3 بازاردان Is Not an Executable Feature in the Current Scope

«بازاردان» is treated as a future platform/shell concept and planning term, not as an approved executable MVP feature.

No agent may create a بازاردان shell, UI, API, schema, dependency, deployment configuration, or other implementation artifact until a dedicated scope review and the required ADR(s) are approved.

### 2.4 Temporary Product Naming Decision

Until a final commercial/brand decision is approved:

| Concept | Temporary canonical name | Legacy / alias handling |
|---|---|---|
| Platform | **Farakhorasan Platform** | Older Farakhorasan platform variants are historical aliases |
| Sales module | **Forooshyar Sales** | «فروشیار», «Farakhorasan Sales OS» and prior sales labels may remain as legacy references where needed |
| Future organization/platform shell | **Farakhorasan Platform shell** | «بازاردان» remains a future concept/working label, not an executable feature |

Legacy branding must not be used as the basis for new architecture, routes, database identifiers, packages, or UI naming without explicit review.

### 2.5 Implementation Gate

Starting implementation is permitted only after:

1. the relevant ADR is accepted;
2. scope review confirms the feature belongs to the active phase/cut line;
3. architecture impact is identified;
4. required acceptance criteria are defined;
5. the implementation is assigned to the active Workstream.

For multi-tenant infrastructure or بازاردان shell work, this gate is mandatory even if the requested change appears small.

---

## 3. Consequences

### Positive

- Platform and sales-module boundaries become explicit.
- Multi-tenancy cannot be accidentally downgraded to a future nice-to-have.
- بازاردان cannot silently become a parallel product scope.
- Legacy branding is contained without requiring a rename/refactor now.
- Agents have a clear governance gate before implementation.

### Trade-offs

- Some naming ambiguity remains temporarily for historical documents.
- Future schema/API work for multi-tenancy must wait for its implementation design and scope review.
- Product branding is intentionally not finalized by this technical ADR.

---

## 4. Non-Goals of This ADR

This ADR does **not**:

- modify database schema;
- add or modify API endpoints;
- change UI;
- add dependencies;
- change deployment configuration;
- implement multi-tenancy;
- implement بازاردان;
- authorize a new MVP feature;
- finalize commercial branding.

---

## 5. Required Follow-up

Before any implementation PR related to these topics:

- update `PROJECT_STATE.md` and Roadmap status;
- update `docs/CONFLICT-MATRIX.md` if the scope or decision changes;
- create or update the required ADR;
- perform Scope Review;
- keep implementation PRs separate from governance/documentation PRs.
