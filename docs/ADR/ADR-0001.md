## 1. Context

در طول مرحله طراحی، دو مجموعه سند در مورد پشته فناوری پروژه وجود دارد:

1. **مستندات طراحی (`Markdown/PDF`)** — که بر اساس آنها معماری دامنه، bounded contexts و قواعد کسب‌وکار تعریف شده است. این اسناد در نسخه اصلی به پشته‌ای مبتنی بر `FastAPI + SQLAlchemy + Pydantic` اشاره داشتند.
2. **کدبیس جاری در مخزن** — که بر پایه `Express 5 + JWT + Pino` و `PostgreSQL + Drizzle ORM` و فرانت‌اند `React 19 + Vite + TS + Tailwind + shadcn/ui` ساخته شده است.

این اختلاف عمداً پنهان نشده، ولی تا زمانی که به‌صورت رسمی و مکتوب حل نشود، هر توسعه‌ی بعدی در انتخاب تکنولوژی و قراردادها با ابهام مواجه خواهد شد.

**نکته تکمیلی درباره تصمیم‌های این گپ:**
- کاربر تصمیم‌های صریحی برای محدوده MVP و مدل دامنه داده است (ثبت سفارش/مشتری/ویزیتور/پورسانت به‌عنوان اولویت، تفکیک CustomerProfile/Location/Contact/CreditProfile، ویزیتور به‌عنوان User، پورسانت بر پایه target/performance + order value، approval supervisor→admin، Rule Engine با seed + UI).
- هدف این تصمیم، تعیین تکلیف **مرجع استک و مرجعیت سندها** است تا این تصمیم‌ها پشت یک مرجع قاطع پیاده‌سازی شوند.
- مخزن به‌صورت **چند ارگانی** باید ساختار یابد، اگرچه پیاده‌سازی MVP از یک شرکت شروع می‌شود.

**شرط تعریف‌شده:** پیاده‌سازی باید روی **کدبیس فعلی** انجام شود تا از تکرار کار و گسست با پروژه جلوگیری شود.

## 2. Decision We Are Taking

### 2.1 مرجعیت (Source of Truth)
- **حاکمیت، معماری دامنه و قواعد کسب‌وکار** ← از **مستندات طراحی (`Markdown`)** می‌آید.
- **پشته فنی اجرایی، قراردادهای کد و پیاده‌سازی** ← از **کدبیس فعلی مخزن** می‌آید.
- «علت محصول» از Markdown و «چگونگی اجرا» از کدبیس حاصل می‌شود.

### 2.2 تکنولوژی اجرایی نهایی
- **Backend:** `Express 5 + JWT + Pino`
- **API Contract:** OpenAPI (`openapi.yaml`) → Orval → React Query + Zod
- **Database/ORM:** PostgreSQL + Drizzle ORM
- **Frontend:** React 19 + Vite + TypeScript + Tailwind + shadcn/ui
- **Monorepo:** pnpm workspaces
- هر اشاره‌ی قدیمی به `FastAPI/SQLAlchemy/Pydantic` در مستندات اولیه، **سابقه طراحی تاریخی** است و مرجع پیاده‌سازی نیست مگر با ADR جداگانه.

### 2.3 مرجع دامنه و قواعد
مدل دامنه و قواعد (بسته‌های دامنه، KPI، Rule Engine، پورسانت، اعتبار، Soft Delete، Audit Trail و تفکیک امتیاز اعتباری از پورسانت ریالی) از Markdown مرجع می‌آیند و در لایه کد با قراردادهای Repository پیاده‌سازی می‌شوند.

### 2.4 Multitenancy
- MVP از یک سازمان شروع می‌شود.
- با این وجود، **زیرساخت ذخیره‌سازی باید از ابتدا چندارگانی/چندمستاجری (Multi-tenant) در نظر گرفته شود**؛ مفهوم `organization_id` و مرجع سازمان در جداول حساس بخشی از معماری الزامی است.
- این تصمیم صرفاً «قابلیت آینده» نیست؛ **الزام معماری** است.

## 3. Clarification Introduced by ADR-009

ADR-009 رابطه و نام‌گذاری محصول را روشن می‌کند:

- **Farakhorasan Platform** نام سطح پلتفرم است.
- **Forooshyar Sales** نام ماژول/محصول فروش درون پلتفرم است.
- نام‌های قدیمی و legacy branding تا زمان تصمیم تجاری/برندی نهایی، در اسناد به‌عنوان alias یا historical reference علامت‌گذاری می‌شوند و نباید مبنای ایجاد معماری یا تغییرات کدی جدید قرار گیرند.
- هر توسعه‌ای که مرز پلتفرم، multi-tenancy، shell سازمانی یا بازاردان را تغییر دهد، پیش از کدنویسی نیازمند ADR و Scope Review مصوب است.

این بخش، تصمیم‌های ADR-0001 درباره مرجعیت و multi-tenancy را شفاف‌تر می‌کند و جایگزین آنها نمی‌شود.

## 4. Consequences

### 4.1 Experience
- رفع ابهام استک.
- مرجعیت روشن برای دامنه و اجرا.
- ادامه توسعه روی کدبیس جاری بدون بازنویسی غیرضروری.
- جلوگیری از دوباره‌کاری.

### 4.2 الزامات بعدی
- مستندات قدیمی FastAPI باید برچسب تاریخی داشته باشند.
- قواعد دامنه باید با Decision Record یا Master Specification قابل ردیابی باشند.
- تغییر معماری باید ADR جدید داشته باشد.
- multi-tenancy باید در Scope و Architecture Gateهای قبل از کدنویسی کنترل شود.
